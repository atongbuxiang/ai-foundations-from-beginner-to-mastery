# 训练实验协议、事故记录与因果证据地图

> [!abstract] 本节目标
> 把前七节合成一套可审计、可证伪、可交接的 research ledger。你将能在运行前写 claim/estimand/protocol，在运行中保存 manifest/telemetry/deviation，在失败后形成 postmortem，在结果后按证据等级限制结论。

## 一、研究账本不是实验结束后的整理工作

如果运行前没有声明问题和边界，实验后很容易发生：

- 从十几个 metric 中挑一个改善的；
- 把失败 run 删除；
- 事后改变 checkpoint/seed；
- 把 recipe bundle 的效果归给单一组件；
- 只保存赢家配置，无法重建搜索预算；
- 在相同 validation 上反复迭代，却报告为独立评估。

所以 research ledger 应贯穿

$$
\text{claim}
\to\text{design}
\to\text{execution}
\to\text{diagnosis}
\to\text{analysis}
\to\text{decision}
\to\text{handoff}.
\tag{1}
$$

它不是“多写文档”，而是让结论和原始证据之间存在可追踪映射。

## 二、第一张表：Claim–Estimand Contract

每个核心 claim 建唯一 ID，例如 `C-TRN72-01`，填写：

| 字段 | 示例 |
|---|---|
| claim | 在固定 50B tokens 下，recipe B 降低 validation loss |
| treatment | B 相对 A 的完整 optimizer+schedule bundle |
| experimental unit | pretrained checkpoint × data seed block 内的一次训练 |
| outcome | 冻结 checkpoint 的 locked validation token-weighted NLL |
| estimand | block 分布上的 paired mean difference |
| margin | loss 至少下降 0.02 才有实践意义 |
| target scope | 该模型 family、数据版本与硬件/precision 范围 |
| competing explanations | tuning budget、data order、precision、failure selection |

用潜在结果语言可写

$$
\Delta=\mathbb E_B[Y(B)-Y(A)],
\tag{2}
$$

其中下标 $B$ 指预先声明的 block/target distribution。[[S-2025-Hernan-Robins-What-If]] 的意义在于：让“比较谁”与“对谁平均”不可隐去。

## 三、第二张表：运行前 Protocol

Protocol 至少锁定：

1. hypothesis/claim IDs、primary/secondary/exploratory outcomes；
2. factor levels、control、randomization、pairing/blocking；
3. train/data/FLOP/time/tuning budgets；
4. seed hierarchy、replication 数、power/MDE；
5. telemetry level、invariants、failure definition；
6. checkpoint/evaluation/selection/early-stop；
7. fixed-$n$ 或 sequential stopping 和 multiplicity；
8. code/data/config/env versions 与 test access policy；
9. analysis plan、missing/failure/censoring 处理；
10. 可接受的 protocol deviations 与审批/记录方式。

探索实验可以更灵活，但必须标 `exploratory`；确认实验的关键在于分析自由度在看结果前受约束。

## 四、第三张表：不可变 Run Manifest

每次 launch 生成 `run_id`，manifest 至少包括：

```yaml
run_id: trn72-A-s07-20260826T1030Z
claim_ids: [C-TRN72-01]
protocol_version: p3
code_commit: ...
config_hash: ...
data_manifest_hash: ...
model/checkpoint_hash: ...
seed: {init: 7, data: 19, dropout: 31}
budget: {tokens: 5.0e10, max_steps: ..., wall_hours: ...}
precision/distribution/hardware: ...
selection_rule: ...
artifact_root: ...
```

hash 的作用是识别对象，不是保证语义正确；仍需保存 human-readable diff 和 schema version。敏感凭证绝不能写入 manifest。

## 五、第四张表：事件与 Telemetry Ledger

用 append-only 事件表记录：

| event_id | clocks | type | object | value/artifact | code/config context |
|---|---|---|---|---|---|
| e001 | wall/micro/update/token | launch | run | manifest hash | p3 |
| e128 | ... | alert | layer 17 activation | z=9.2 | telemetry L1 |
| e129 | ... | snapshot | checkpoint/batch/RNG | artifact hash | replayable |
| e154 | ... | deviation | world size changed | approved/reason | p3+d1 |

Telemetry 保存聚合窗口、单位和 sampling rate；否则两个相同字段名可能不是同一量。大 artifact 可外置，但 ledger 必须存 hash、schema、owner 与保留期限。

## 六、第五张表：Trial 与搜索总账

[[S-2019-Dodge-Show-Your-Work]] 与 [[S-2023-Google-Deep-Learning-Tuning-Playbook]] 要求最终结果能回到完整开发过程。每个 trial 记录：

- sampled configuration 与 search-space version；
- sampling algorithm/parent trial；
- allocated/consumed compute；
- early termination 与原因；
- success/failure/censored；
- validation observations 与访问次数；
- selection rank/rule；
- 是否进入 confirmatory evaluation。

只保存 best config 会使 tuning budget、失败率和 winner's curse 无法审计。

## 七、第六张表：训练事故 Postmortem

事故不是备注在 README 的一句话，而是独立记录：

1. summary 与 impact：损失多少 compute/数据、污染哪些结论；
2. detection：谁/哪个 invariant 何时发现；
3. timeline：最后正常、first bad event、mitigation、recovery；
4. trigger、proximate mechanism、contributing conditions、control gap；
5. evidence：日志、tensor、checkpoint replay、反事实；
6. mitigation 与 permanent fix；
7. action items：owner、deadline、verification test；
8. unresolved alternatives 与 residual risk。

[[S-2026-Google-SRE-Postmortem]] 的 blameless 原则用于推动系统改进；它不允许把不确定根因写成确定事实。每条 root-cause assertion 应链接证据等级。

## 八、因果证据地图：从恒等式到跨环境复验

建议为每个 claim 标记最高完成等级，而不是笼统写“已验证”：

| 等级 | 证据对象 | 允许的结论 |
|---|---|---|
| E0 合同/推导 | shape、更新式、estimand、DAG | “问题与预测已定义” |
| E1 单元 oracle | 手算/toy/reference implementation | “局部实现回收预期” |
| E2 观测时间线 | telemetry、first-change、相关结构 | “现象与机制路径相容” |
| E3 随机干预 | paired/factorial、区间、失败分母 | “在该协议内估计 treatment effect” |
| E4 机制干预 | mediator/negative control/dose response | “竞争解释进一步被区分” |
| E5 外部复验 | 新 seed/data/scale/hardware/实现 | “在列明外部范围内稳健” |

E2 不能写成 E3；E3 也不保证跨 family。Evidence level 与 source tier 不同：顶级论文中的一个观察仍可能只是 E2，自己的严格随机实验也只在自身范围内 E3。

## 九、Claim–Evidence Matrix

为每条 claim 建矩阵：

| claim | supporting | contradicting/null | missing | decision |
|---|---|---|---|---|
| C1 B 降低 loss | E3 paired study | task-2 null | large-scale E5 | conditional adopt |
| C2 原因是谱平衡 | E2 UWR/spectrum timeline | FP32 control unchanged | mechanism intervention | hypothesis only |
| C3 B 更省成本 | throughput E2 | tuning budget higher | total-R&D audit | unresolved |

必须保留 null/contradicting evidence。证据地图不是宣传材料，而是给后来者指出“当前能说什么、还不能说什么”。

## 十、复现有多个层级

结合 [[S-2021-Pineau-ML-Reproducibility]] 与 [[S-2026-PyTorch-Reproducibility]]，分开：

1. **artifact integrity**：文件/hash/schema 完整；
2. **same-code rerun**：同环境按容差/bitwise 重跑；
3. **independent reimplementation**：根据方法合同另写实现；
4. **statistical replication**：效应分布和区间在新 runs 重现；
5. **external validity**：在新 data/model/scale/hardware 范围复验。

`seed=42` 只涉及其中很小一部分。复现目标应在 protocol 中预先声明，不应在 bitwise 失败后临时改称“趋势一致”。

## 十一、Protocol deviation 怎么处理

现实运行会遇到坏节点、数据修订和安全停止。Deviation 不一定使实验作废，关键是：

- 发生前能否预见，是否与 outcome 相关；
- 是否影响 treatment 对称性、预算或 selection；
- 谁在何时、看过哪些结果后作决定；
- primary analysis 是否按原 protocol 保留；
- 是否另做 per-protocol/sensitivity analysis。

严重 deviation 后应提升 protocol version 并重新开始确认集，而不是把新旧 runs 静默混合。

## 十二、一个卷终项目应交付什么

本卷项目不是“跑出更高分”，而是提交一个完整、可审计的训练比较包：

- 1 个 preregistered claim/estimand/DAG；
- 1 个至少 $2^2$ factorial 或有充分理由的替代设计；
- 预设配对、区间、margin 与停止规则；
- 1 次真实失败运行，不得人为制造后只留截图；
- first bad event、checkpoint/batch/RNG/env 复现包；
- 修复前后 replay/control/quality 对照；
- 完整 trial/failure/compute/checkpoint ledger；
- claim–evidence matrix 与至少一个未解决竞争解释；
- 独立复跑说明和 artifact hashes。

删除失败记录的“完美实验”不通过审计，因为它破坏 failure denominator 和事故学习链。

## 十三、从个人实验到团队交接

交接文档应让未参与的人在不询问作者的情况下回答：

1. 当前最佳结论和适用边界是什么？
2. 哪些配置/数据/代码精确产生它？
3. 失败率、预算和 selection 是什么？
4. 哪条证据支持每个机制断言？
5. 下一项最有信息价值的实验是什么？
6. 哪些 artifact 受权限/保留期限制？

若只能重跑命令却无法解释 estimand，或能解释论文却找不到 artifact，都不算真正交接。

**怎样读图**：从左侧 claim/estimand 进入 protocol 和 immutable manifest，运行产生 telemetry/trials/incidents；分析输出正反证据矩阵，decision 带着范围进入下一版 claim，所有箭头都可追溯到 artifact hash。

**图没有证明什么**：账本完整不等于假设正确，也不保证 DAG、实现、统计功效或外部有效性成立；它只能让错误更容易被发现、复算、反驳和纠正。

## 十五、核心结论

成熟训练研究的产物不是一个 checkpoint，也不只是一篇解释，而是 claim、协议、运行、失败、选择、统计和 artifact 之间的可追踪网络。研究账本的最高价值，是让后来者能区分“已证明”“在该协议下支持”“仅与机制一致”和“仍未解决”。
