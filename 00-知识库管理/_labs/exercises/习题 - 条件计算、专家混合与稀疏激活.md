# 习题 - 条件计算、专家混合与稀疏激活

## A. 识别与复述

### ARCH-MOECAP-A01
用一句公式说明 dense FFN 与 sparse MoE 在“总参数—每 token 激活计算”上的差别。

### ARCH-MOECAP-A02
区分 total parameters、activated parameters、resident parameters 与 MACs。

### ARCH-MOECAP-A03
说明条件计算与“所有专家都算完再平均”的普通集成有何不同。

## B. 手算与建模

### ARCH-MOECAP-B01
设 $d=1024,m=4096$。计算忽略偏置的 dense FFN 参数量与每 token 主 MAC 数。

### ARCH-MOECAP-B02
设 $E=16,k=2,m_e=1024,d=1024$。计算专家总参数、激活专家 MAC，并与 $m=4096$ 的 dense FFN 比较比例。

### ARCH-MOECAP-B03
给定 $E=8,k=2,m_e=m/2$，解释为何“专家参数 4×、专家主计算 1×”不矛盾。

## C. 推导与证明

### ARCH-MOECAP-C01
推导在固定 dense width $m$ 与目标参数倍数 $R$ 下，$E,m_e$ 应满足的关系；再给出等激活 MAC 对 $k$ 的约束。

### ARCH-MOECAP-C02
在被选专家输出两两正交时，证明组合输出范数平方的分解式，并指出非正交时多出的项。

### ARCH-MOECAP-C03
写出包含 shared expert 的参数与每 token MAC 主项，说明 shared width 为何是 always-on 成本。

## D. 边界、反例与纠错

### ARCH-MOECAP-D01
反驳：“MoE 每 token 只激活 2/64 专家，所以参数显存必然缩小 32 倍。”

### ARCH-MOECAP-D02
构造 total parameters 增大但模型质量不升的反例机制。

### ARCH-MOECAP-D03
解释为何 activated parameters 不能直接预测 decode latency。

## E. AI 迁移

### ARCH-MOECAP-E01
为 dense 与 MoE 写一条等激活计算的质量比较协议。

### ARCH-MOECAP-E02
为目标集群写一张 MoE 端到端成本账，至少含六项。

### ARCH-MOECAP-E03
设计检验“Router 在预测专家输出幅度”的实验，并区分相关与因果。
