# 细粒度专家、共享专家与动态激活

> [!abstract] 核心问题
> “专家更多”至少可能来自三条不同轴：把同一参数预算切成更多小专家、增加所有 token 都经过的共享专家、让每 token 激活数动态变化。它们分别改变组合空间、基线计算与资源分配，必须分开记账和消融。

## 一、先把三条设计轴正交化

设 routed expert 数为 $E$、每个宽度为 $m_e$、每 token 激活数为 $k_t$，shared expert 总宽度为 $m_s$。一个简化层为

$$
y_t=x_t+f_s(x_t)+\sum_{i\in I_t}w_{ti}f_i(x_t).
$$

专家参数主项

$$
P\approx 2dm_s+E\cdot2dm_e,
$$

每 token 专家主 MAC

$$
C_t\approx2dm_s+k_t\cdot2dm_e.
$$

由此看出：shared width $m_s$ 是 always-on 成本；fine-grained 改 $E,m_e$；dynamic activation 改 $k_t$ 的分布。

## 二、细粒度专家是什么

假设原方案有 $E$ 个宽度 $m$ 的专家。把每个专家切成 $r$ 个宽度 $m/r$ 的小专家，得到 $E'=rE$。若忽略偏置：

$$
E'\cdot 2d(m/r)=E\cdot2dm,
$$

总专家参数近似不变。若同时令每 token 激活 $k'=rk$ 个小专家，激活 MAC 也近似不变：

$$
k'\cdot2d(m/r)=k\cdot2dm.
$$

但是候选组合数从 $\binom Ek$ 变为 $\binom{rE}{rk}$，Router 输出维度、排序成本、专家 batch size 与通信粒度都改变。所谓“同参数同计算”只控制了主矩阵乘，不代表系统完全相同。

[[S-2024-Dai-DeepSeekMoE]] 把更细的 routed experts 与共享专家结合，目标是提高专家组合的灵活性并减少 routed expert 对公共模式的重复学习。

## 三、共享专家是什么

shared expert 对所有 token 都激活，可视为 dense baseline path。若有 $S$ 个共享专家，每个宽度 $m_s/S$，只要全部执行，总计算仍约为 $2dm_s$。

常见解释是：共享路径学习通用知识，routed experts 专注差异化知识。[[S-2025-Su-10945-MoE共享细粒度专家]] 对这种解释给出直观分析，也提醒“完美均匀的 routed load”未必等于任务最优。

但“共享=公共知识”属于 `H`。证明它需要：

- 控制总参数与激活 FLOPs；
- 比较同宽 dense path、共享专家和额外 routed experts；
- 分析干预/移除后哪些 token 或能力受损；
- 检查不同层、seed 的表示与路由稳定性。

若只观察 shared expert 高频激活，没有信息量，因为它按定义就对所有 token 激活。

## 四、动态专家数的两类定义

### 1. Token budget 动态

令 token $t$ 根据难度或不确定性选择 $k_t$：

$$
k_t\in\{0,1,\dots,k_{\max}\}.
$$

可以用累计概率阈值、margin、entropy 或 learned controller 决定。总 assignment 预算可能约束为

$$
\sum_tk_t\le B.
$$

### 2. Expert quota + threshold

对每个专家维护阈值 $\beta_i$：

$$
A_{ti}=\mathbf1[s_{ti}-\beta_i>0].
$$

每 token 的 $k_t=\sum_iA_{ti}$ 自动变化，而 $\beta_i$ 通过 quantile/反馈让每专家接收接近 quota。这里动态性来自列配额约束，不是显式预测“难度”。

[[S-2026-Su-11626-MoE动态激活]] 强调了这一区分：去掉逐 token 恰好 Top-k 的约束，不等于取消 expert-side 的负载预算。

## 五、“难 token 应用更多专家”是待检验命题

[[S-2025-Su-10815-MoE动态专家]] 探讨按 token 难度动态分配专家数。直觉合理：简单 token 少算，困难 token 多算。但至少有三个反例方向：

1. 高 entropy 可能来自不可约噪声，多算无益；
2. Router 不确定可能表示专家都不合适，而非应同时调用更多；
3. 训练中频繁 token 可能因价值大而值得更多预算，即使它们并不“难”。

所以 difficulty 指标、额外 expert 的边际收益和预算约束必须共同验证。一个有用指标是

$$
\Delta_t(r)=L_t(k_t=r)-L_t(k_t=r+1),
$$

即多给一个专家的损失边际改善，而不是只看当前 token loss。

## 六、动态激活的成本不只看平均 $\mathbb E[k_t]$

若平均激活数固定，方差仍会影响系统。对设备并行，step time 更接近最忙专家/设备负载：

$$
T_{\text{step}}\gtrsim \max_i T_i,
$$

而非简单由 $\mathbb E[k_t]$ 决定。大量 token 在同一时刻提高 $k_t$ 会造成通信 burst。还需报告 $k_t$ 的分位数、与 sequence position/语言/损失的相关性，以及每专家负载尾部。

## 七、K3 等近期系统报告怎样使用

[[S-2026-Su-11848-K3-MoE-Attention]] 总结了一个近期开发系统中 Stable LatentMoE、RMSNorm、Quantile Balancing 与近似全局 quantile 等组合。它对“这些组件怎样拼接”具有高价值，但属于开发者系统报告 `E/H`，不是独立 benchmark，也不能从整体系表现识别每个组件的因果贡献。

其中用 histogram/有限 bins 近似 quantile 是很好的工程案例：数学对象是全局分位点，实现对象是离散直方图近似；二者误差需要单独验证。

## 九、三轴因子实验

最低限度做 $2\times2\times2$ 设计：

- shared on/off；
- coarse/fine-grained；
- fixed/dynamic $k$。

并提供两条控制：

1. **等总参数**：调整 $E,m_e,m_s$；
2. **等激活 MAC**：调整 $k_t$ 平均值与 shared width。

同时报告 quality、total/active parameters、router cost、expert batch size、All-to-All bytes、load tail、kernel occupancy。若一次同时打开三项，只能评价组合方案。

## 十、证据边界与学习出口

- 参数与 MAC 分账、阈值产生动态 $k_t$：`I`；
- 给定分配模型的预算性质：`T`；
- DeepSeekMoE/K3 等报告结果：其协议下 `E`；
- “共享公共知识”“困难 token 需要更多专家”：`H`；
- 跨规模最优粒度/shared ratio/dynamic policy：`O`。

学完本节，应能在固定参数和固定激活 MAC 下换算粗/细专家，分离 shared 与 routed 成本，并设计检验“动态多算是否真正给高边际收益 token”的实验。
