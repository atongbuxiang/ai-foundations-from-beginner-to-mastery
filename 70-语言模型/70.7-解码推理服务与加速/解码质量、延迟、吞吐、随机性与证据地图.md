# 解码质量、延迟、吞吐、随机性与证据地图

> [!abstract] 一句话结论
> 解码实验不是找一个“最好参数”，而是识别 model、decoder 与 server 的联合系统在质量、分布、延迟、吞吐、内存和成本上的 Pareto 前沿；每个主张都必须绑定对象层、负载、指标、方差与复现合同。

## 一、先固定评估对象

同一个 checkpoint 可因 prompt template、logit processors、sampler、stop、scheduler 与硬件得到不同观测。至少分三层：

1. **raw model**：固定 token history 时的 logits 或 $p_\theta$；
2. **decoder**：temperature/truncation/constraint/search/RNG 定义的序列分布 $q(y\mid x)$；
3. **serving system**：到达、排队、batch、KV、kernel 与故障策略形成的 output-and-timing process。

“模型更随机”“top-$p$ 更快”“PagedAttention 质量更高”常因跨层而失去可证伪含义。实验表第一列应写明被改动和保持固定的层。

## 二、四类质量证据

| 证据族 | 典型指标 | 主要问题 |
|---|---|---|
| 任务质量 | accuracy、pass@k、ROUGE、reward、人工偏好 | 输出是否解决任务 |
| 分布行为 | entropy、distinct-n、self-BLEU、重复率、support size | decoder 产生怎样的样本族 |
| 有效/安全 | schema pass、citation correctness、toxicity、tool validity | 输出能否被约束消费 |
| 可靠性 | calibration、worst-group、failure rate、置信区间 | 结果跨样本/子群是否稳定 |

单一 perplexity 不能选择通用解码器；自动指标也可能与人工判断错位。解码策略的排名常随任务类型变化，因此基线、prompt 集与任务分层必须预注册。对有争议的 min-$p$ 实证主张，应保留原始方法定义，同时不把未经可靠对照支持的优越性写成定论。

## 三、延迟时间线

对请求 $i$，记录到达 $a_i$、开始 prefill $s_i$、首 token 返回 $f_i$、各 token 返回 $t_{i,j}$、完成 $c_i$：

$$
\operatorname{TTFT}_i=f_i-a_i,
$$

$$
\operatorname{TBT}_{i,j}=t_{i,j}-t_{i,j-1},
\qquad
\operatorname{E2E}_i=c_i-a_i.
$$

常见 TPOT 可取首 token 之后的平均间隔，但必须说明是否包含网络/streaming flush。用户体验同时受 TTFT 和尾部 TBT 影响；只用 E2E/输出 token 数会把排队与 prefill 摊薄，掩盖首 token 等待。

报告 p50/p95/p99 而非只有均值，并给 bootstrap CI 或多轮重复。极端长 prompt、长输出和并发突发应单独分层。

## 四、吞吐、goodput 与饱和曲线

吞吐定义要写单位：output tokens/s、total tokens/s 或 requests/s。提高 arrival rate 时，系统通常经历低负载区、利用率上升区、饱和区和队列爆炸区。峰值吞吐若对应不可接受的 TTFT，没有服务意义。

设 SLO 指示为

$$
I_i=\mathbf 1[\operatorname{TTFT}_i\le \tau_f,
\ p99\operatorname{TBT}_i\le\tau_b,
\ \text{valid}_i=1],
$$

则时间窗口 $\Delta$ 内 request goodput 为

$$
G=\frac{\sum_i I_i}{\Delta}.
$$

也可定义满足 SLO 的 token goodput，但不可与 request goodput混用。测量应扫 arrival rate/concurrency，画出 goodput 与 tail latency，而非只选一个幸运负载点。

## 五、随机性有三个层次

- **分布复现**：两实现是否从同一理论 $q(y\mid x)$ 采样；
- **统计复现**：有限样本的频率、均值与 CI 是否兼容；
- **轨迹/字节复现**：固定输入与 seed 是否得到完全相同 token 序列。

分布精确的 speculative decoder 可以因 RNG 消耗次序不同而不具备逐字节同 seed 对齐。反之，两实现偶然生成同一条样本也不证明分布相同。

小词表可做 exact enumeration：比较每个输出概率。大词表可固定 prompt 集，使用 paired seeds 以降方差，但仍要做多 seed；对 sampler 分布可比较 token/sequence frequencies、KL/TV 的可估计代理或两样本检验。若目标是字节复现，另存 RNG algorithm/state/counter、kernel、batch membership 与 processor order。

## 六、Pareto 而非总冠军

对配置 $c$，观测向量可写为

$$
u(c)=(Q(c),-\operatorname{TTFT}_{99}(c),
-\operatorname{TBT}_{99}(c),G(c),-M(c),-C(c)).
$$

若另一配置在所有关心维度都不差且至少一维更好，$c$ 被支配；否则它可能位于 Pareto frontier。业务效用或 SLO 才能从前沿选点。不要把质量、速度、成本随意归一后相加而不披露权重。

有用的配对设计：同一 prompt、同一模型、相同最大输出与 stop；逐一改变 decoder 或 scheduler。随机输出用多 seed；服务测试固定 arrival trace 并交叉轮换配置，避免温度、缓存和背景负载漂移。

## 七、最小实验矩阵与数据字典

| 维度 | 最低记录项 |
|---|---|
| 模型 | checkpoint hash、dtype/quantization、tokenizer/template |
| decoder | processor 顺序和参数、constraint、sampler/beam、stop/max tokens、RNG |
| 服务 | engine/commit、scheduler、KV block/dtype、parallelism、hardware |
| workload | prompt/output length 分布、arrival trace、concurrency、warm/cold、数据版本 |
| 输出 | token IDs、finish reason、validity/quality、错误/重试 |
| 时间 | arrival/prefill/first-token/per-token/complete timestamps |
| 统计 | 样本数、seed、重复轮次、CI、p50/p95/p99、排除规则 |

日志中 per-token timestamp 会增大开销；应先测 instrumentation overhead，或在固定比例请求上采样。失败请求不可从分母静默删除。

**读图问题**：一次“配置更好”的主张应先落在哪个对象层，又要怎样沿 request trace 和 Pareto 前沿同时核对质量、尾延迟与成本？

**怎样读图**：先沿 model→decoder→server 确定改动与控制变量，再在同一 workload 上读取 queue、TTFT、TBT 和完成；最后只在不被支配点中依据预注册 SLO/效用选配置。

**图没有证明什么**：教学 request trace 和 Pareto 点不支持任何真实引擎的性能排名，也不支持某种 sampler 在所有任务上占优；缺少真实负载、重复试验与置信区间时不能外推。

## 九、常见错误与出口标准

错误包括：不分 raw model/decoder/server；只报均值或峰值；tokens/s 单位含糊；离线固定 batch 外推在线队列；用一个 seed 评价随机策略；把同 seed 不同输出判为分布错误；失败样本静默删除；不同任务的指标直接平均。

完成本节后，应能设计一张干预清晰的评估矩阵，计算 TTFT/TBT/goodput，区分三种复现，识别 Pareto 支配，并为任一“更快/更好/完全等价”主张列出可证伪的证据合同。
